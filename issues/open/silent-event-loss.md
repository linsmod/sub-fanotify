# 路径反解失败的事件被静默丢弃：一次 500 文件的 rm -rf 只送达 27%

> **优先级说明（2026-10-06 修订）**：本篇原为 P1，依据是「失败不可见但后果未知」。补测之后
> 按项目自己的判据表重估为 **P0** ——「会静默丢数据」，且**不是罕见路径**：一次普通的
> `rm -rf` 就丢掉 73% 的事件，没有任何日志、没有任何信号。若维护者按「消费者能靠自己的
> 兜底 pass 恢复」而选择留在 P1，那是合理的判断，这里把测量摆出来供决定；同时
> `ISSUE_GUIDELINES.md` 的「当前 issue」表需要同步改成 P0。
>
> 提出者：esidx，sfa 的一个订阅方（只订阅、不 fork、不改 sfa）。所有实测用仓库自己的
> `sfa-server` + `sfa_client` 复现。环境：WSL2 `6.18.40.1-microsoft-standard-WSL2`，sfa
> `eff9956`，mark 协商结果为 `FAN_MARK_FILESYSTEM`（`MOUNT 1/7`、`FILESYSTEM 7/7`）。
> **正文所有 `文件:行号` 以 `eff9956` 为基准**；代码改动后行号会漂移，摘录才是判据。

## 现象

普通事件只在 `resolve_dfid_event()` 成功时才广播，没有 `else`（`sfa-server.c:285-290`）：

```c
if (resolve_dfid_event(mount_fd, fid, is_dirent,
                       ev.path, sizeof(ev.path)) == 0) {
    ev.type     = sfa_primary_type(mask);
    ev.path_len = (uint32_t)strlen(ev.path) + 1;
    broadcast(clients, nclients, &ev);
}
```

同一类静默退出在代码里共**四处**：

| 位置 | 静默条件 | 能否被真实路径触发（实测结论） |
|---|---|---|
| `sfa-server.c:278` | `fid == NULL`，即事件里没有可识别的 info record | 未观察到；DFID_NAME 已协商时看起来是防御性分支 |
| `sfa-server.c:285` | `open_by_handle_at()` 或路径拼接失败 | **能，而且频繁** —— 见下 |
| `sfa-server.c:252` | `oldf` / `newf` / `mask` 任一不成立 | 未观察到 |
| `sfa-server.c:256` | 新旧两条路径之和超过 `path` 缓冲区 | **能，确定性可复现** —— 见下 |

四处都不写日志、不计数、不通知客户端。`README.md:37` 只承诺「`open_by_handle_at` 不可用时告警、丢弃无路径事件」，而这份能力是在**可用**的情况下的实测结果。

### 实测一：删除一棵子树，73% 的事件消失

`resolve_dfid_event()` 失败的主因是**事件被读到时，它引用的父目录已经不存在了**（`sfa-server.c:50` 的 `open_by_handle_at()` 返回 `ESTALE`）。删除比「读事件 + 反解路径」快，所以队列里越靠后的事件越可能已经过期。用两个只差这一点的对照来量：

```sh
# 情况一（平铺）：500 个文件放在同一个目录里，逐个 unlink。父目录一直活着。
# 情况二（嵌套）：同样的 500 个文件分布在 10 个目录里，然后 rm -rf 上一级。
```

```
flat   : DELETE 行 501 / 500     ← 全部送达（多出的 1 条是目录自身 mtime 变化的 ATTRIB）
nested : 事件      139 / 511     ← 只有 27%
         其中 [dir]  19           ← 11 个 rmdir + 若干目录自身的 ATTRIB
OVERFLOW 事件                 0  ← 不是内核队列丢的
代理 stderr                   0  ← 代理一个字都没说
```

唯一的变量就是「事件被读到时父目录是否还存在」。511 = 500 个文件 + 10 个子目录 + 1 个父目录。
两次独立运行分别得到 139/511 和 141/511。

**停摆会把同一个比例推到极端。** 同样是一次 500 文件的 `rm -rf`，但先让代理卡在 `send()` 里
（#1 的形状，用 `SIGSTOP` 造一个不读的订阅者），等树删完再让它继续：

```
代理正常排空时      141 / 511   (27%)
代理先停摆过        1 / 511   (0.2%)   ← 只有最外层那个 rmdir 活下来
OVERFLOW 事件          0
代理 stderr            0
```

所以停摆不是必要条件（正常运行时也丢 73%），但它是把这件事从「大部分」变成「几乎全部」的放大器。

### 实测二：rename 的双路径之和越界

`sfa-server.c:255-256` 把新旧两条路径塞进同一个 `path[SFA_MAX_PATH]`：

```c
size_t n1 = strlen(newp) + 1, n2 = strlen(oldp) + 1;
if (n1 + n2 <= sizeof(((struct sfa_event *)0)->path)) {   /* 4096 */
```

路径长到 2107 字节时，两条之和是 4216 > 4096：

```
深层 rename（新路径 2107 字符）      ->  MOVED 行 0 条
同一时刻的浅层 rename（对照组）     ->  MOVED 行 1 条
代理 stderr                        ->  0 行
```

同时验证了**单路径的长度检查够不着**：一个路径正好是 Linux 允许的最大值 4095 字符的文件，事件正常送达。所以真正的边界不在 `sfa-server.c:67` 那一条，而在双路径之和这一条 —— 这也说明修的时候不能只盯着单路径那处。

## 影响

**对下游是静默的数据丢失，而且是常态不是角落。** 一个把事件流当作「最多落后一个批次」承诺的订阅方，这个承诺的前提是每个事件要么被处理、要么被显式告知丢了。这里两者都不是：一次 `rm -rf` 之后，客户端**收不到任何东西**，索引里那 500 行还在，而没有任何办法区分「这些文件没被改动」和「这些文件的改动事件丢了」。软件包卸载、`git clean`、构建清理、日志轮转 —— 都是这个形状。

**两种丢失对索引的伤害不同，rename 那条更隐蔽：**

| 情形 | 客户端收到什么 | 索引的状态 |
|---|---|---|
| 删除事件丢失 | 什么都没有 | 500 行幽灵行，指向已不存在的文件 |
| rename 事件丢失 | 什么都没有 | 旧名字那一行继续答 `name:旧名字`，新名字永不出现 —— 两边都错，且互相印证不了 |

**量级。** 上面两例都是几百条事件的规模；比例（27%）与规模无关，取决于「删除比读事件快多少」，也就是取决于批量删除的形状 —— 一次几千文件的 `rm -rf` 会更差。

**频率此前标为「未知、不可当作罕见」，现在有数据了**：触发条件是「事件在被读取之前其父目录已被删除」，而这恰好是**任何目录树被删除时的默认情形**。

**对消费者的兜底能力。** 一个有周期性对账 pass 的索引器会退化成「索引变旧」，而不是「索引错到无法察觉」；本项目正是这样，`--refresh` 的空转 pass 在 5 476 485 个条目的树上是 0.4-1.1 ms。所以本篇主张的是**让丢失可见**，而不是「丢失会造成数据损坏」。

## 建议

复用一个已经存在的信号形状，再加一位表示「有事件，但路径反解失败」：

```c
/* sfa.h，紧接 SFA_EV_MOVED */
SFA_EV_UNRESOLVED = 1u << 8,
```

每次 read 批次里只要有失败，就发**一条** `type = SFA_EV_UNRESOLVED`、`path_len = 1`、`path[0] = '\0'` 的事件；同一批次的失败次数与 errno 分布打一行 stderr。

**为什么复用这个形状。** `SFA_EV_OVERFLOW`（`sfa.h:26`）已经表达了「有事件发生了，但内容是空的」这件事，客户端已经有处理路径（标脏 + 退回一次全量）。新增一个同族信号，客户端只需在现有分支上加一个判断，不引入新消息类型、新解析路径。示例客户端也已经能显示它（`sfa_client.c:46` 把无路径事件打印成 `(overflow)`）。

**为什么每批次一条而不是每次失败一条。** 上面的规模下会有 372 条丢失（正常排空）或 510 条丢失
（停摆后），每次一条就是 1.5-2.1 MB 的额外流量，全部是无用信息 —— 而客户端拿到第一条之后的
动作是同一种：补一次全量。精确计数对客户端没有价值，对运维有价值，所以计数放 stderr，
两边各取所需。

**为什么必须能被订阅，而不能无条件推送。** `SFA_EV_OVERFLOW` 是可订阅的位，保持一致比开特例好。代价是**每个订阅方都要自己把这个位加进掩码**：本项目就是这么订阅的（显式掩码，不含 `SFA_EV_ALL`），所以我们会在下一版里加上。也就是说这条信号对**升级前**的客户端仍然无效 —— 它们本来就在静默丢事件，这一点无法靠协议补救。

### 连带影响

1. **必须把新位加进 `SFA_EV_ALL`**（`sfa.h:32-34`）。`broadcast` 按 `clients[i].mask & ev->mask` 过滤（`sfa-server.c:125`），示例客户端订阅的正是 `SFA_EV_ALL`（`sfa_client.c:24`）—— 不加进去，`UNRESOLVED` 会被过滤条件挡掉。
2. **必须加进 `sfa_event_name()`**（`libsfa.c:66-79`），否则打印出来是 `UNKNOWN`。
3. **不必升 `SFA_PROTO_VERSION`。** 消息结构未变，新位只是 `mask` 里的一个 bit；`libsfa.c:31-35` 的严格版本校验会让所有现有客户端硬失败（`EPROTO`），而升级并不带来任何好处 —— 老客户端收到不认识的位不会崩，只是看不见这条信号。
4. **四处失败应收敛到一个内部 helper。** 否则四处各写一遍，将来各自漂移，而这份 issue 的全部价值就在于「它们不是同一件事」。
5. **`README.md:37` 那一行需要改。** 现在写的是「`open_by_handle_at` 不可用 → 告警，丢弃无路径事件」，读者会得出「可用时就没有丢弃」的结论，而实测否定了这个结论。至少补一句「已协商成功时仍可能因句柄过期而丢弃」。
6. **可选的、更彻底的修法（比本篇的诉求大，列出来供判断）**：给目录句柄做一张 `handle → path` 缓存。DFID_NAME 记录本身就是「父目录句柄 + 名字」，父目录在缓存里就能直接拼出路径，不必再去打开那个可能已经消失的目录。要解决的问题是：缓存条目随目录一起失效（rmdir 时淘汰、目录 rename 时用 `SFA_EV_MOVED` 更新新名）、以及「同一批次内创建又删除的目录」这种仍然够不着的情况。这条能消掉实测一里的绝大部分丢弃，但它是独立的一块工作，不该绑在这个 issue 上。

## 附注

- **esidx 侧已经准备好了**：收到无路径事件时，我们把它当成「有东西发生了但我无法枚举」，把索引根标脏做一次全量，并计数告警（`watch.c` 的 `esidx_watch_drain()`，`watch_stats_t.unresolved`）。所以这条信号对我们是零成本的接线，不是新逻辑 —— 现在缺的只是信号本身。
- **相关**：#1（代理一旦停摆，同一次 `rm -rf` 的送达率从 27% 掉到 0.2% —— 停摆不是丢失的必要条件，是放大器）、#3（socket 权限）。
- **不在本 issue 范围内**：能否从内核侧拿到更可靠的路径（`FAN_REPORT_FID` + 目录句柄缓存见上面第 6 条）；`FAN_EVENT_INFO_TYPE_FID`（非 DFID_NAME）事件的路径语义；示例客户端的输出格式。

## 维护者决定（2026-10-06）

STATUS: accept，保持 **P0**

REASON: 本篇正对着这个项目的核心交付物（`README.md:16`「reporting every event as it happens,
as an absolute path」）。路径反解失败的时序窗口是 fanotify API 的形状决定的 —— 只给 handle、
路径必须事后重建 —— **这个窗口必然存在，不可能靠实现技巧消掉**。所以问题从来不是
「有这个窗口」，而是**窗口不告诉你**。把「让丢失可见」当成这个项目本该有的东西，
而不是当补丁 —— 这决定了它排 P0 而不是 P1。

关于本篇开头「优先级说明」里留给维护者的判断：**采纳 P0**，依据是判据表「会静默丢数据」那一条，
且触发条件是任何目录树被删除时的默认情形，不是罕见路径。

一处修正，记在正文里供后来人核对：`sfa-server.c:278`（`fid && mask`）与 `:252`
（`oldf && newf && mask`）属于「内核没给出必要信息」，与 `:285`、`:256` 那两处
「有信息但没能产出路径」性质不同。收敛成一个 helper 时不该让它们共用同一个失败计数器，
否则 stderr 上的计数会把「内核没给」和「我们没解出来」混成一件事。

NEXT（验收标准）：

1. `sfa.h` 新增 `SFA_EV_UNRESOLVED = 1u << 8`，并入 `SFA_EV_ALL`（不加会被
   `sfa-server.c:125` 的掩码过滤挡掉），并加入 `sfa_event_name()`；
2. 一次 500 文件的 `rm -rf`，客户端**能收到**无路径信号事件，且能据此做一次全量；
3. `README.md:37` 补一句：已协商成功时仍可能因句柄过期而丢弃；
4. `SFA_PROTO_VERSION` **不升**（结构未变，老客户端只是看不见这条信号，不是崩）；
5. stderr 上的失败计数按批次聚合，附 errno 分布；
6. 四处失败收敛到一个内部 helper，其中「内核没给」与「反解失败」分开计数。

**与 #1 的关系（2026-10-06 决定）**：两篇**不合并** —— 根因不同（fanout 背压 vs 路径重建时序），
验收标准也不同，合并会让两件事都验不了。但两者**必须共用同一个丢失信号形状**：
新增 `SFA_EV_UNRESOLVED` 是 `SFA_EV_OVERFLOW` 的同族信号，#1 的 desync 补发也走它，
不另开第三种语义。这条作为约束写在这里和 #1 里。
