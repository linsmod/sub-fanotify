# 消息头没有 reserved 字段、版本校验不协商：改结构的代价是全量客户端重连

> 提出者：维护者本人，在给 #2 / #4 / #6 做决策时读出来的。**本篇没有实测需求，
> 全部结论来自读代码**，标注见各处。

## 现象

三个消息结构里，两个留了扩展位，只有最常改的那个没有。

`struct sfa_welcome`（`sfa.h:70-74`）与 `struct sfa_subscribe_req`（`sfa.h:64-67`）都有
`uint32_t reserved`。`struct sfa_event`（`sfa.h:52-61`）**没有**，而且排布上也没有空位：

```c
struct sfa_event {
    uint32_t type;        /* 4 */
    uint32_t mask;        /* 4 */
    uint32_t pid;         /* 4 */
    uint32_t path2_off;   /* 4 */
    uint64_t timestamp;   /* 8 */
    uint32_t path_len;    /* 4 */
    uint32_t flags;       /* 4 */
    char     path[SFA_MAX_PATH];
};
```

头部 32 字节，按 8 字节对齐排满，**加任何字段都会改变 `sizeof`**，
而 `sfa_recv()` 靠 `sizeof` 判定消息完整性（`libsfa.c:57`），客户端一侧无法做前向兼容。

版本校验是严格相等（`libsfa.c:31-35`，见 #6 正文摘录）：不认识就 `EPROTO` 断开，
**没有协商、没有兼容路径、没有能力查询**。

## 影响

**同一个扩展动作，代价相差两个数量级。** 已有的三个决定恰好横跨这条线：

| 扩展 | 是否改结构 | 实际代价 |
|---|---|---|
| 加一个 `SFA_EV_*` 位（#2） | 否 | 0 —— 老客户端看不见这条信号，不崩 |
| 复用 `SFA_EV_OVERFLOW` 补发 desync（#1） | 否 | 0 |
| 给 `sfa_event` 加 `uint64_t seq` | 是 | 全部客户端重连，且**必须**重连 |

也就是说：**协议里唯一「便宜」的扩展方向恰好是位掩码**，而位掩码能表达的东西很有限
（一个事件类型位，最多 32 个），表达不了序列号、表达能力协商、表达不了任何结构化字段。

**「全量重连」在本项目里不是小事**：客户端是索引器，重连期间要么停止实时更新退回轮询，
要么自己补一次全量。项目并不保证有全量能力，客户端能不能补、补多久，是客户端自己的事。

## 建议

**本篇现在只记录约束，不定方案。** 三条候选，各有代价，没有明显的最优：

1. **给 `sfa_event` 加 `uint64_t reserved[2]`（或一个 `reserved` + 一个 `seq`）**，
   预留头部空间，代价是消息从 4128 变 4144 字节（`sfa.h:52-61`，满路径时），
   且**这一次就要升版本**，之后所有头部扩展免费。
2. **版本区间而非严格相等**：客户端声明「我认识 1~2」，服务端在交集里选。
   代价是引入「服务端可能比客户端旧」这类新状态，以及选择失败时的行为定义。
3. **引入能力查询消息**（客户端连接后先问再定订阅），把兼容性从版本号移到能力位上。
   代价是一次额外往返，且仍要解决「新客户端连老服务端」的方向问题。

**倾向 1**，理由是它把「一次性付全量重连的成本」变成「一次性」，而 2 和 3 都只是
把成本推迟并复杂化。但这是取舍，不是结论。

## 影响范围与前置条件

- **#6（协议级前缀过滤）在 #7 有结论之前不动。** 否则会把「全量重连」再叠一次。
- **#2 不受影响**：它走位掩码，结构未变，已决定不升版本。
- **#1 不受影响**：复用已有信号形状。
- **不要为了「预留而预留」顺手加字段。** 加了 `reserved` 就要有明确的填充规则
  （谁填零、旧客户端收到非零时怎么处理），否则只是把一个已知成本换成一个未知成本。
