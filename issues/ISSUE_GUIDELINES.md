# Issue 指南

sfa 的问题与改进提案都用仓库内的 markdown 文件记录，新 issue 建在 `open/` 下。一份 issue = 一个**可定位、可讨论、可落地**的问题。

这份文档只讲怎么写。文件名取 kebab-case，与标题主干一致：`blocking-send-backpressure.md`。

## 提交之前

先看下面的[当前 issue](#当前-issue)列表，确认要提的问题不重复。已经写过的，在那一篇里补充即可，不要另开一份——同一个问题散成多篇，讨论时很容易只改到其中一篇。

## 结构

四段，顺序固定。

### 标题：一句话讲清「现象 + 后果」

不写「关于 X 的建议」，也不写提案式标题。写发生了什么，以及它导致什么。

- ✗ 关于广播背压的建议
- ✓ broadcast 用阻塞 send，一个慢客户端能把特权代理卡死

### 现象：`文件:行号` + 真实代码摘录

让读者不打开代码就能确认问题是真的。行号会漂移，所以**摘录的代码本身比行号更重要**，两者都给。

**行号要注明基准 commit**（例如「行号基于 `eff9956`」）。代码一改行号就失效，而读者没有义务去猜它基于哪一版—— 失效的行号比没有行号更坏，它会把人引到错误的位置上。已修复的 issue 在「修复与实测」里记录改动之后的新基准。

### 影响：为什么值得改

至少回答一个问题：

- 对下游是否致命 —— 会不会静默丢数据、客户端能不能自己发现
- 量级多大 —— 一条事件的成本、触发频率、缓冲能装几条
- 不修的后果 —— 是隐患，还是已经在某个场景里发生

### 建议：可落地的方案

给出具体改法，并说明**为什么选这个而不是别的**。只写「应该加个过滤」不算建议。

代价、局限、已知不覆盖的情况，写在这里，不要留给读者自己发现。

### 附注（可选）

相关文件、相关 issue，以及明确**不在本次范围内**的部分。

## 规则

1. **一个 issue 一件事。** 能独立讨论的两件事拆成两份。

2. **现象必须可定位。** 给 `文件:行号` 和摘录，不转述、不猜测。

3. **事实与推测分开。** 实际验证过的写「实测」并附命令或输出；没验证的明确标「假设」。混在一起会让读者无法判断结论有多可靠 —— 一个未经确认的因果关系，写成结论就是在制造假信心。

4. **建议要能落地。** 说清选了什么、代价是什么。有讨论结论时把结论补回 issue，包括否掉的理由和替代方案，避免下次重复讨论。

5. **把连带影响列出来。** 改一处通常不止一处：协议结构变了要同步版本号与 SDK，权限变了要同步 README，启动参数变了要考虑解析顺序。漏掉的连带项会变成下一个 issue。

## frontmatter

文件开头带 YAML frontmatter，新建时填成这样：

```yaml
---
id: 5
status: open
type: bug
priority: P1
created: 2026-10-06
closed:
commit:
verdict:
---
```

| 字段 | 怎么填 |
|---|---|
| `id` | 顺延现有编号（当前最大是 8，新 issue 用 9） |
| `status` | 新建一律 `open` |
| `type` | `bug` / `feature` / `docs` / `chore` |
| `priority` | 自己判断，见下 |
| `created` | `YYYY-MM-DD` |
| `closed` / `commit` / `verdict` | 新建时留空 |

**优先级怎么定。** 按后果定，不按修复难度定：

| | 判据 |
|---|---|
| `P0` | 破坏文档已承诺的能力，或会静默丢数据、卡死整条链路 |
| `P1` | 正确性问题：结果不对、失败不可见，但不影响可用性 |
| `P2` | 量级与扩展性：能做但不划算，噪声、带宽、协议开销 |
| `P3` | 杂项：文档、注释、可读性 |
